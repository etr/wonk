3. [x] **performance-reviewer** | `src/reach.rs:319` | algorithmic-complexity
   *Addressed (majors sweep, 2026-10-02):* already fixed upstream (ReachGraph::load finalizes candidate lists).
   caller_candidates (src/reach.rs:238-255) rebuilds a HashMap<usize,f64> with_capacity(refs.len()), collects it into a Vec, and sorts it with a String-comparing (file, line) closure every time a BFS expands a name — once per (source, expanded-name) pair. The fan-out cap (max_targets=500) bounds recorded rows but NOT this cost: the full candidate list is materialized and sorted before the cap check inside the candidate loop, so a hub name's entire list is paid in full even when only 500 rows survive. In the synthetic bench names are unique (f{m}_{j}), so each list is tiny and the delta is only 0.97s; on realistic 100k-symbol repos, name-keyed BFS collides generic callee names ('new', 'get', 'init') repo-wide — refs_by_name['new'] can hold tens of thousands of entries — and every source whose traversal discovers any symbol with that name (e.g. any helper called by a constructor) re-pays an O(k log k) string-heavy sort of the whole list. Hundreds-to-thousands of such sources x several ms each can add seconds-to-minutes of build time, exactly the hub-heavy quadratic the task asked about. child_candidates (lines 258-268) has the same clone+sort-per-call shape for type-edge children.
   *Recommendation:* Memoize the sorted candidate list per distinct name: either precompute candidates_by_name / sorted_children_by_name once after ReachGraph::load (total cost = one sort pass over all references, O(sum k log k)), or lazily cache per name in a RefCell<HashMap<String, Rc<Vec<(usize,f64)>>>>. This turns per-source expansion into an O(1) lookup and removes the recomputation entirely while preserving the deterministic order the equivalence suite locks. Optionally skip the cap check re-evaluation by iterating a shared slice.
